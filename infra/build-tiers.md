# 在沙箱里跑构建：已知事实与待办

当前阶段的多机实验直接在 worker 上跑可信代码，不经过沙箱；本页这件事暂缓。这里记录两类内容：已经实测到的事实（只经沙箱平台的公网接口取得，不登录节点），以及以后把构建 worker 放进沙箱时要做的事。

## 已知事实（示例环境）

| 问题 | 实测 |
| --- | --- |
| 沙箱看到的 CPU 数 | `nproc`、`os.cpu_count()`、亲和性都是宿主的 128，而 cgroup 配额只有申请的那几个核。按核数开线程的程序（包括 `lean` 和 `lake`）会按 128 来开 |
| PID 上限在哪 | 容器自己的 cgroup 里 `pids.max` 显示很大；每 Pod 128 的上限设在 Pod 的上级 cgroup 上，容器里看不到这个数字，但会被它限制 |
| 身份与权限 | 以 uid 0 运行，所有 capability 都被去掉，`NoNewPrivs=1`；没有挂载 ServiceAccount token（环境变量里仍有 `KUBERNETES_*`） |
| 外网 | GitHub、PyPI、Lean 的发布站和包索引都能访问，单次请求 0.2–2 秒 |
| 内网 | 出站全开，能连到 K8s API、共享盘服务器、节点的 SSH 和 kubelet。是安全问题，见 scheduling.md 的“出站” |
| 沙箱之间 | 一个沙箱连另一个沙箱的执行端口被拒，入站策略生效；沙箱之间不能直接通信 |
| 后台进程 | 在一次命令里放到后台的服务，在命令结束后没有存活。需要常驻进程时，要用平台的后台执行方式，或者在入口命令里启动 |
| 基础镜像里的工具 | 基础 Python 镜像只有 `tar`、`gzip`，没有 `git`、`curl`、`zstd`、编译器 |
| 启动时装工具链 | 第一次尝试时，解包到 `/tmp` 的安装程序执行被拒（PermissionError），原因未查明（可能是 `/tmp` 不允许执行，或解包时丢了执行位） |
| 根盘 | 容器里看到的是节点整块盘的容量；临时盘上限由 kubelet 统计后驱逐来执行，不体现为文件系统大小 |

共享盘和节点间网络的实测见 storage.md、scheduling.md。

## 以后要做的事

按依赖顺序：

1. **出站网络策略**：拒绝内网网段，只放行 DNS、公网和明确需要的内网服务。这一条不只关系到构建，现有沙箱就有这个暴露面，应该最先做。
2. **线程与 PID**：
   - 给构建设单独的 PID 上限档位（kubelet 的 PID 上限是整节点统一的，可以专门划一组节点，或调整认证基线）。
   - 在镜像里默认限制每个 `lean` 进程的线程数（`-j` / `--threads`），并实测 N 个并发编译时的线程峰值。
3. **工具链**：
   - 查明 `/tmp` 下不能执行的原因。
   - 二选一：启动时安装（每次几十秒到几分钟，依赖外网）；或者走镜像流程预装（见 images.md，需要先把流程通用化）。
4. **构建目录**：
   - 给沙箱挂 `<local>` 上的目录，容器内路径固定；或者申请足够大的临时盘。
   - 平台的临时盘预约是所有调用方共用的一个总额，要一起核算。
5. **通信方式**：沙箱之间不能直连，所以 worker 只能主动连出去（连协调服务和产物库）。产物库放在沙箱能访问、又不暴露其他内网服务的位置。
6. **专用调用方**：
   - 只有沙箱权限，镜像精确到 digest。
   - 并发 8–12、累计约 32 CPU / 128 GiB、单实例 6 小时，有效期 90 天。
   - 同时核对命名空间配额（和其他调用方共用）与三台节点的可分配量（合计约 61 CPU）。
   - Key 只发给运行协调服务的机器，不进沙箱，不进仓库。

# 接入说明

## 新节点接入沙箱池

| 步骤 | 做什么 | 怎样核对 |
| --- | --- | --- |
| 1. 摸底 | 只读查 CPU、内存、各块盘的余量和归属、负载、系统版本、宿主上已有的容器服务 | `node_check.sh`、`io_sample.sh` |
| 2. 选盘 | 按 storage.md 给运行时数据 `<runtime-dir>`、构建目录 `<local>` 选空闲的本地盘；确认 kubelet 目录所在的盘也有足够余量 | `node_check.sh` 的 runtime、kubelet、local 三项为 PASS |
| 3. 共享盘 | 挂上 `<shared>`，路径与其他 worker 一致；UID 与其他 worker 一致 | `node_check.sh` 的 shared 各项 |
| 4. 宿主参数 | `vm.max_map_count` 写进 `/etc/sysctl.d/` 并生效 | `node_check.sh` 的 vm.max_map_count 为 PASS |
| 5. 加入集群 | K8s 发行版的 agent 配置：数据目录、节点标签（`enabled=true`、`tier=worker`）、预留量、驱逐阈值、每 Pod PID 上限 | 节点 Ready |
| 6. 隔离认证 | 核实这台节点当前 boot 的 PID 上限确实生效，由定时任务打上认证标签（不手工补） | 节点带认证标签 |
| 7. 预载镜像 | 把所有已准入的镜像按 digest 导入并 pin | 节点上镜像列表与其他 worker 一致 |
| 8. 进池 | 把它加进 `EXPECTED_NODES`；网关副本数随节点数调整 | `cluster_check.sh` 无 FAIL |
| 9. 验证 | 跑 stability.md 的 V0–V2，并确认新节点上至少落过一个实例 | 报告里有这台节点 |

移出节点的顺序反过来：先把 `enabled` 改成 `false`（同时写进节点配置），等它上面的实例自然结束或按归属删除，再做维护。

## 任务 worker 怎样使用沙箱

给以后在沙箱里跑构建任务的 worker 定的约定：

| 项 | 约定 |
| --- | --- |
| 入口 | 只走公网 HTTPS 入口和平台 SDK/REST；不依赖内网地址、K8s 凭据或节点 SSH |
| 身份 | 每类任务一个专用调用方，只有沙箱权限；授权写明并发、累计 CPU/内存、单实例最长时间、允许的镜像 digest |
| 创建 | 按 digest 指定镜像；写明 CPU、内存、临时盘、时长；带固定幂等键（任务 ID + 序号）；带归属元数据，便于对账 |
| 时长 | 时长要盖住一次分片的耗时；长任务按需续期，续期不能超过授权的累计上限 |
| 输入 | 小文件经平台的文件接口上传；大输入放 `<shared>` 的任务目录，只读挂入 |
| 执行 | 在容器内固定的工作目录里构建；限制每个进程的线程数，使总线程数在 PID 上限内 |
| 输出 | 打包成大文件，先写临时名再改名，放到 `<shared>` 的任务目录；或经文件接口下载 |
| 结束 | 删除实例并确认回收；失败、超时同样删除；中断后按归属元数据对账，不留残余 |
| 不放进沙箱的东西 | 任何凭据（平台 Key、仓库 token、kubeconfig）；源码当不可信数据，复核在可信机器上做 |

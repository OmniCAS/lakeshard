# 为大型仓库的多机构建准备沙箱集群

lakeshard 要把一个超大的 Lean 仓库拆开，放到多台机器上并行构建，构建任务都在沙箱里跑。这个目录记录这套沙箱集群的基础设施该怎么准备：节点要满足什么、数据落在哪里、怎样只调度到指定节点、镜像怎么构建和发放、怎样判断服务稳定，以及新节点和任务 worker 怎么接入。

内容是通用的，不对应某一套具体机器。文中的数字来自一套示例环境，用来说明量级和取舍。

## 脚本

都是只读检查，参数用环境变量或命令行给出，不含任何真实地址。

| 脚本 | 用途 |
| --- | --- |
| [scripts/node_check.sh](scripts/node_check.sh) | 在一台节点上检查 CPU、内存、本地盘余量、运行时与 kubelet 目录所在的盘和驱逐余量、共享挂载参数与卡顿次数、`vm.max_map_count`、同一路径 |
| [scripts/cluster_check.sh](scripts/cluster_check.sh) | 在能访问集群的地方检查：符合调度条件的节点是否正好是指定的那几台、节点健康、入口网关副本分布、配额、沙箱 Pod 落点 |
| [scripts/io_sample.sh](scripts/io_sample.sh) | 采样各块盘的忙碌程度，判断哪块盘空闲 |
| [scripts/stability.py](scripts/stability.py) | 按档位跑创建 → 文件往返 → 执行 → 删除 → 确认回收，统计落点；后端可插拔，自带内存假后端 |

测试：`python -m pytest infra/tests`（只用标准库和 pytest）。

## 约定

| 写法 | 含义 |
| --- | --- |
| `hub` | 入口与控制面所在的机器，不跑沙箱 |
| `worker-1`、`worker-2`、`worker-3` | 跑沙箱的节点 |
| `<shared>` | 各 worker 都挂着的共享目录 |
| `<local>` | worker 上用来放构建产物的本地盘目录 |
| `<runtime-dir>` | 容器运行时的数据目录（镜像层和容器可写层） |
| 沙箱平台 / K8s 集群 / 镜像仓库 | 分别指提供创建、执行、回收接口的沙箱服务，它背后的 K8s 集群，以及存放镜像的 OCI 仓库 |

## 示例环境

| 角色 | 规格 | 说明 |
| --- | --- | --- |
| hub | 16 核 32 线程，125 GB 内存，机械盘 + 一块未使用的 NVMe | 控制面、公网入口、鉴权与额度账本 |
| worker-1/2/3 | 各 2 路 64 核 128 线程，503 GB 内存，本地 SATA/NVMe SSD 1.8–7.2 TB | 与其他用户的 GPU 任务共用，沙箱能用的 CPU/内存由预留量压到一小部分 |
| 共享盘 | 一台 NFS 服务器，经独立 10 GbE 存储网挂到三台 worker，约 15 TB、剩约 3 TB | hub 不在存储网上 |

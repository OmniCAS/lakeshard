# 稳定性验证

原则：低并发、稳定优先。先保证几个到十几个实例长期可靠，再谈高并发。每一档都要证明三件事：

- 操作成功：创建、命令、文件往返都成功。
- 落点正确：每个实例都在指定节点上。
- 回收干净：删除后能正面证明实例和它的资源都不在了。光靠时长到期或记录消失不算证明。

## 档位

| 档位 | 内容 | 通过标准 |
| --- | --- | --- |
| V0 健康 | `cluster_check.sh` 和每台的 `node_check.sh`；入口的健康接口 | 符合调度条件的节点正好是 worker-1/2/3，都 Ready、无压力、无阻塞污点；网关 ≥2 个副本在不同节点；配额和平台账本为空；没有 FAIL |
| V1 串行 | 连续 20 轮完整生命周期：创建 → 写 64 KiB 随机文件 → 在沙箱里算哈希并写成新文件 → 读回两个文件 → 删除 → 确认回收 | 20/20；记录每轮节点和各步耗时 |
| V2 低并发 | 实例保持存活，依次增长到 1、2、4、8、12；每档所有存活实例执行一条标记命令，新实例做一次文件往返 | 每档全部成功；落点只在三台；结束后账本、Pod、配额归零 |
| V3 重复 | “同时创建 8 个 → 检查 → 全删”连续 3 轮 | 3/3 通过；没有鉴权 503、就绪超时或残留 |
| V4 持续 | 6 个实例存活 25–30 分钟（不超过调用方的单实例时长上限），每 30 秒做一次命令和文件往返 | 零失败；结束后归零 |
| V5 镜像 | 核对三台的预载镜像列表（按 digest）；每个已准入的镜像经平台起一次 | 三台列表一致；实例直接启动，不在运行时拉镜像 |

每档实例的规格要小（例如 0.1 CPU / 512 MiB / 1 GiB 临时盘），不和真实任务抢资源。大规格实例单独验收，先核算四层额度（见 scheduling.md）和宿主余量。

三台都要证明能用：按整次运行统计落点，V1–V4 合起来每台至少落过一个实例（运行器的 `--require-all-nodes`）。不按每一档要求，因为调度器按可分配量的比例打分，小实例会集中到可分配量最大的那台。如果整次运行都没落到某台，先查那台的调度条件和打分，再考虑给沙箱模板加一个软的按主机名打散约束（`whenUnsatisfiable: ScheduleAnyway`）。

## 运行器

`scripts/stability.py` 实现了 V1–V4：

```bash
python infra/scripts/stability.py --backend fake --tier serial:3 --tier ramp:1,2,4 \
  --allowed-nodes worker-1,worker-2,worker-3 --require-all-nodes --out report.json

python infra/scripts/stability.py --backend my_adapter:make_backend --backend-config adapter.json \
  --tier serial:20 --tier ramp:1,2,4,8,12 --tier repeat:8x3 --tier soak:6:1800:30 \
  --allowed-nodes worker-1,worker-2,worker-3 --require-all-nodes --op-timeout 180 --out report.json
```

- 后端是一个小接口（create、node、write、read、run、delete、absent、owned、close），平台适配器放在仓库外。凭据由适配器自己从私有位置读，不放进 `--backend-config`。
- 报告是 JSON：每个实例的节点、各步耗时、检查次数、错误、是否证明回收；每档的节点分布；整个运行结束后平台上还剩的实例（应为空）。
- 任何一步失败都会记录下来，并在 `finally` 里删除本次运行创建的所有实例。

## 常见故障与规则

| 现象 | 真实含义 | 规则 |
| --- | --- | --- |
| 创建请求超时或连接断开 | 服务端可能已经创建了实例 | 创建必须带固定的幂等键（同一运行 + 序号）。失联后只重放同一个请求身份，再按操作记录或归属元数据对账。不能为了掩盖未知结果而新建 |
| 创建成功，但等待就绪超时 | 实例存在，可能已经在运行 | 按实例 ID 删除并证明回收；记为失败，不重试成别的实例 |
| 鉴权服务偶发 503 | 入口到鉴权服务的一次调用失败 | 只对只读、幂等的操作做有界重试；创建按上一条处理 |
| 运行中断（脚本被杀、SSH 断开） | 可能留下实例 | 用同一个 `--run-id` 对账：先列出本次运行还在的实例并删除，再开新的运行 |
| 删除返回成功 | 只是请求被接受 | 必须查到实例和 Pod 都已不存在，才算回收 |

## 判断“稳定”

V0–V4 连续两次全部通过，而且中间隔开至少一天，才算这一阶段稳定。任何一档失败，先查清原因（节点、网关、鉴权、客户端），改完从 V0 重来。不要靠反复重跑凑出一次通过。

## 示例环境的结果（第一次完整运行）

62 个实例全部落在 worker-1/2/3（分别 4、11、47 个），hub 和池外节点一个都没有；每个删除都有回收证明，结束时平台上本次运行的实例为 0。

| 档位 | 结果 | 创建 p50 / p95 | 删除到证明回收 p50 |
| --- | --- | --- | --- |
| V0 | 通过 | — | — |
| V1 串行 20 | 20/20 | 13.0 s / 17.2 s | 3.0 s |
| V2 1→2→4→8→12 | 12/12 | 15.3 s / 19.5 s | 22.5 s（12 个同时删） |
| V3 8×3 | 24/24 | 17.6 s / 24.3 s | 15.1 s |
| V4 6 个 25 分钟 | **未通过**：35 轮后，6 个实例在同一秒一起失败 | 15.0 s / 21.8 s | 13.1 s |

V4 的原因：
- 入口的访问日志里，这 25 分钟共 2,000 多个请求，只有那一秒的 6 个运行时请求返回 503。
- 错误码表示入口去外部鉴权服务核验调用方 Key 失败。入口对每个请求都现场核验，没有缓存，也没有重试，所以鉴权服务约 1 秒的不可用打断了所有在途实例。

修法：
- 入口侧：对核验成功的结果做 30–60 秒的短时缓存，核验失败时对鉴权服务做一次有界重试。
- 调用方侧：只读、幂等的请求遇到这个 503 时做有界退避重试。

修完后从 V0 重跑。

从这次运行看到的两点：
- 串行创建全部落在可分配量最大的那台；只有并发创建才会分散到其他节点。所以“三台都能用”要按整次运行统计。
- 同时删除 12 个实例时，回收证明的耗时是单个删除的 7 倍左右，批量回收的超时要按并发数放宽。
